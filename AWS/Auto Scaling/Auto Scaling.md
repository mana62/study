# Auto Scaling
**負荷に応じてEC2インスタンス台数を自動で増減してくれる仕組み**

## Auto Scalingを使う目的
### ① 性能維持
- アクセス増えても落ちにくい

### ② コスト削減
- 必要な時だけ増やす
- 暇な時は減らす

### ③ 自動復旧
- EC2が故障したら新しいEC2を起動可能

### ④ 運用負荷軽減
- 夜中に人が増減操作しなくていい


## スケーリングタイプ
### ① 垂直スケーリング（Scale Up）
- **サーバー1台を強くする方法**

例：
- t3.micro → t3.large
- CPU増強
- メモリ増強
- 小さいPC → 高性能PC

**メリット**
- 簡単
- 台数管理不要

**デメリット**
- 上限がある
- 再起動必要な場合あり
- 1台壊れると弱い

### ②水平スケーリング（Scale Out）
**サーバー台数を増やす方法**
Auto Scaling はこっち

`1台 → 3台 → 10台` ＝ Auto Scaling

**メリット**
- 障害に強い
- 柔軟に増減可能
- AWS向き

**デメリット**
- ELB必要
- 構成管理必要

## Auto Scalingコンポーネント
### 1. 起動テンプレート（Launch Template）
- 新しいEC2を作る設計図

含む内容：
- AMI
- インスタンスタイプ
- セキュリティグループ
- IAMロール
- キーペア
- User Data

つまり：新しいEC2を増やす時のレシピ

### 2. Auto Scalingグループ（ASG）
- EC2集団の管理本体

設定例：
- 最小台数：2
- 希望台数：2
- 最大台数：10
- 常に2台以上維持
- 最大10台まで増える

### 3. スケーリングポリシー
- 「いつ増やす？いつ減らす？」ルール

例① CPU使用率
- CPU 70%以上が5分続いたら +1台

例② リクエスト数
- アクセス数増えたら +2台

例③ スケジュール
- 毎朝9時に5台へ増やす

### 4. 終了ポリシー
- 減らす時、どのEC2を消すか

例：
- 古いEC2から削除
- AZバランス見て削除
- 最新以外を削除

## スケーリング種類
### 1. Target Tracking（初心者おすすめ）
- CPU50%を維持するよう自動調整
- 一番使いやすい

### 2.Step Scaling
- 70%超えたら+1台
- 90%超えたら+3台
- 細かい制御可能

### 3.Scheduled Scaling
- 毎日9時増やす、深夜減らす
