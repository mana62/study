# インターフェイス

## インターフェイスとは
- **オブジェクトの形を定義するための設計図**
- JSには存在せず、コンパイル時だけの型チェック専用の仕組み

例：
```ts
interface Human {
  name: string;
  age: number;
  greeting(message: string): void;
}
```
意味：
- この形をしたオブジェクトを Human と呼びますという宣言
- プロパティ名・型・メソッドのシグネチャ（引数・戻り値）を決める
- 実行時（ブラウザで動くJS）には完全に消える

```ts
// 使う時
const human: Human = {
  name: 'taro',
  age: 30,
  greeting(message: string) {
    console.log(message);
  },
};
```
- human が Human の形を守っているかを TypeScript がチェックしてくれるだけ
- JSに変換されたら interface Human { ... } は一切残らない

## interface と typeエイリアス の違い
👉 **「オブジェクトを書くのに特化している」**
👉 **「type は何でも型にできる万能エイリアス」**

| 項目 | interface | type（タイプエイリアス） |
|------|-----------|---------------------------|
| 表せるもの | 主にオブジェクトの形 | なんでも（ユニオン、プリミティブ、タプルなど） |
| 拡張の仕方 | extends で継承 | &（交差型）で合成 |
| 同じ名前を再宣言 | マージされる（追加される） | エラーになる |
| JSに残るか | 残らない（型だけ） | 残らない（型だけ） |


共通点：
- どちらも「型に名前をつける」もの
- オブジェクトの形を表現できる

```ts
// type
type HumanType = {
  name: string;
  age: number;
};

// interface
interface HumanInterface {
  name: string;
  age: number;
}
```

#### メソッドの書き方の違い
```ts
interface Human {
  // 関数型として書く
  greeting: (message: string) => void;

  // メソッド記法（オブジェクトのメソッド専用）
  greeting2(message: string): void;
}
```
- どちらも型としては同じ意味
- クラスのメソッドっぽく書きたいなら後者が好み、くらいの違い

## interfaceのメリット
- オブジェクトを書くときに読みやすい
-  クラスと相性が良い（implements）
-   宣言マージが便利（ライブラリ拡張）
-   つまり オブジェクトの設計図 として自然に読める から

- 逆に、ユニオン型を定義する時は、typeの方が強力

## implementsとは（クラスとインターフェイス）
- implements: このクラスは、このインターフェイスの形を必ず守りますと言う意味

```ts
// 設計図（interface）
interface Human {
  name: string;
  age: number;
  greeting(message: string): void;
}

// 設計図どおりに作るクラス（implements）
class Developer implements Human {
  constructor(public name: string, public age: number) {}

  greeting(message: string): void {
    console.log('hello ' + message);
  }
}
```
ポイント：
- **Developer は Human が要求するプロパティを全部持っていないとエラー**
- 必ず使うよと宣言しているから
- greet を書き忘れたらエラー
- 型チェックのためだけの仕組み（JSには存在しない）

## interfaceでのpublic / private / protected / readonly
- インターフェイス側では：
  - public / private / protected は書けない
  - **readonly だけ書ける**（書き換え禁止（初期化時だけOK））

```ts
interface Human {
  readonly name: string; // 読むだけ、書き込み不可
  age: number;
}
```
クラス側では：
- public / private / protected / readonly すべて使える
- でも インターフェイスは「外から見える形」だけを表す ので → private なものはインターフェイスにはそもそも出てこない

```ts
class Developer implements Human {
  // name は読み取り専用にしたい
  constructor(public readonly name: string, public age: number) {}
}
```
## 構造的部分型
- TypeScript は**名前ではなく中身の形で型を判断する**

例：
```ts
interface Human {
  name: string;
}

interface Dog {
  name: string;
}

const h: Human = { name: "taro" };
const d: Dog = h; // ← OK
```

なぜ？：
- Human と Dog は 名前は違うけど、形が同じ
- TS は「形が同じなら同じ型」とみなす
**→ これが 構造的型システム**

## 部分型（subtype）
- **より詳しい（情報が多い）型は、よりざっくりした型として扱える**

例：
```ts
interface Human {
  name: string;
}

interface Developer {
  name: string;
  skill: string;
}
- Developer は Human より 情報が多い

// 代入してみる
const dev: Developer = {
  name: "taro",
  skill: "TypeScript",
};

const h: Human = dev; // ← OK
```
なぜ OK？
- Human が要求しているのは name だけ
- Developer は name + skill を持っている
- 最低限 Human の条件を満たしている
だから OK

⚠️ 逆はできない

## 構造型と部分型の必要性
👉 TypeScript の型システムの土台がこの2つ

- 構造的型がある理由
→ JS は「形が合ってればOK」という世界だから
→ TS もそれに合わせて「名前じゃなくて形で判断」する必要があった

- 部分型がある理由
→ JS は「余計なプロパティがあっても動く」世界だから
→ TS も「必要なものが揃っていればOK」という柔軟さが必要だった

つまり、
JavaScript の自由さを壊さずに、型安全を追加するために生まれた仕組み
TypeScript は JavaScript を壊さずに型安全にするために、
構造的型と部分型という柔軟な仕組みを採用した

```bash
┌──────────────────────────────┐
│   TypeScript の型システムの土台 │
├──────────────────────────────┤
│ ① 構造的型（structural typing）│ ← 形で判断する世界
│ ② 部分型（subtyping）         │ ← 情報が多い型は少ない型に入る
└──────────────────────────────┘
```

- 構造的型：
→ 名前じゃなくて「形」で判断する

- 部分型：
→ 情報が多い型は、情報が少ない型として扱える

この2つがあるから
→ JS の自然な書き方が TS でもそのまま動く
→ でも型安全も守れる

## readonly をインターフェイスで使う
- このプロパティは書き換え禁止

```ts
interface Human {
  readonly name: string;
  age: number;
}

const h: Human = { name: "taro", age: 20 };

h.name = "jiro"; // ❌ エラー
h.age = 21;      // OK
```
- type でも同じように使える
- クラスの readonly と同じ意味

## extends（interface）と type の違い
- interface は **継承（extends）できる**
- type は “合成（&）” する

### interface の extends（継承）
```ts
interface Human {
  name: string;
}

interface Developer extends Human {
  skill: string;
}

const dev: Developer = {
  name: "taro",
  skill: "TS",
};
```
→ **Human のプロパティを引き継いで、さらに追加できる**

### type の &（交差型）

```ts
type Human = {
  name: string;
};

type Developer = Human & {
  skill: string;
};
```
→ **Human と { skill } を「合体」させた型**

## まとめ
- implements：クラスが「この設計図どおりに作ります」宣言
- public/private/protected/readonly：クラスの“見える/見えない”の話
- 構造的部分型：TSは“名前じゃなくて形”で型を判断する
- readonly（interface）：プロパティの書き換え禁止
- extends（interface）：設計図を継承して広げる
- type の &：型を合体させる
