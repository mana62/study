# 関数のユニオン型（関数 | 関数）

## 「ユニオン型」とは？
**A | B = 「AかBのどちらか」型**

## 関数同士を|でつなぐと？
```ts
type Func1 = (a: number) => number
type Func2 = (a: string) => string

type UnionFunc = Func1 | Func2

// 呼び出し側
declare const fn: Either // Eitherは「NumberFuncかもしれないし、StringFuncかもしれない」という型

fn(42)      // ← これ大丈夫？
fn("hello") // ← これ大丈夫？
```
上記だと、パラメータと戻り値がこうなる：
- パラメータ：インターセクション型（number & string）
- 戻り値：ユニオン型（number | string）

「かもしれない」状態なので、どちらを渡していいかわからない

- fn が NumberFunc なら → 42 はOK、"hello" はダメ
- fn が StringFunc なら → "hello" はOK、42 はダメ

❗️ TypeScriptは **「どっちを渡しても絶対に安全」なものしか許可ない**
- numberでもありstringでもある値 → そんなものは存在しない → **never（呼び出し不可）**

## なぜパラメータがインターセクションになるのか？
- `UnionFunc`は`Func1`かもしれないし`Func2`かもしれない
- → numberを渡したら、もし実体がFunc2（string期待）だったら型安全が壊れる
- → だから両方が受け入れられる型（= インターセクション）しか渡せないようにしている
- number & string は現実には存在しない型なので never になる
- → つまりその関数を呼び出すこと自体ができなくなる


## まとめ
- 関数 & 関数 → オーバーロード（全パターンを処理できる関数を作る）
- 関数 | 関数 → パラメータがnever→ほぼ呼び出せなくなる

⚫︎ &（インターセクション）→ オーバーロードになる。全パターン対応が必要
⚫︎ |（ユニオン）→ パラメータが厳しくなりすぎて、基本的に使いづらい（理解だけでOK）


| 状況 | 説明 | 問題点 | 解決策 |
|------|------|---------|---------|
| 関数A と 関数B の両方に対応したい | どちらの引数パターンでも受け取れる関数を作りたい | A | B どちらの型かわからないと中で安全に処理できない | **関数オーバーロードを使う** |
| 引数の型が A | B のユニオン型 (A \| B) | 呼び出し側は渡せるが、関数内部では A か B かわからない | 何を渡せばいいかわからず、内部で型エラーになる | **オーバーロードで「呼び出し側の型を確定」させる** |
| オーバーロードなしで A \| B を受け取る | 1つの関数でまとめたい | 内部で型ガードが必要になり複雑化 | 呼び出し側の型推論も弱くなる | **オーバーロードで複数の呼び出しパターンを宣言する** |
| オーバーロードを使う | 関数の呼び出しパターンを複数宣言できる | 呼び出し側は「どのパターンで呼んでいるか」が明確になる | 内部実装は1つでOK | **最も安全で読みやすい** |

- & → 両方のパターンで呼び出せる（便利）
- | → どちらか確定させないと呼び出せない（基本使わない）
