# 複数デコレータの実行順
ルール：
① ファクトリの呼び出し → 上 → 下
② デコレーターの実行 → 下 → 上

#### 覚え方
```bash
@Component(...)   ← **カッコがある** = 評価時点で即実行される = **カッコがあれば評価（上から下）**のタイミングで呼ばれ
@Logging          ← **カッコがない** = 評価しても何も起きない = **カッコがなければ実行（下から上）**のタイミング
```


### TypeScriptがデコレータを処理するとき、2段階ある
- ステップ1: 各デコレータを「評価」する → 上から下へ
- ステップ2: 評価で得た関数を「実行」する → 下から上へ
👉 この2ステップは常に同じ。混乱するのは「評価した結果が何か」が違うだけ。

## シンプルデコレータ（下 → 上）
- 下 → 上 の順で実行される
- ステップ1（評価・上から下）
```bash
@A を評価 → 関数Aそのものが手に入る
@B を評価 → 関数Bそのものが手に入る
```

```ts
@A
@B
class X {}

// 実行順
B → A
```

## デコレータファクトリ（引数など、上 → 下）
- 上 → 下 の順で実行される
- 関数B を実行
関数A を実行
評価がほぼ一瞬なので、「実行：B→A」しか目に見えない


```ts
@Component({ template: "..." })
@Logging
class X {}

// 実行順
Component → Logging
```

## なぜ違うの？
- シンプルデコレータ → 関数そのもの（デコレーターは「関数のネスト（入れ子）」だから下から実行される）
- デコレータファクトリ → 「関数を返す関数」なので、まず上から評価される

👉
ファクトリは「デコレーターを作ってるだけ」

👉
入れ子になるのは「作った後」だけ

---
👉 順番が2つあるから混乱してるだけ

① 作る順番 → 上から
② 使う順番 → 下から
🔸 ① まず「デコレータファクトリ」を捨てて考える
@A
@B
class X {}

👉 これはこう👇

A(B(X))

👉 だから

B → A

👉 ここはOKですよね

🔸 ② 次にファクトリだけ見る
@A()
@B()

👉 これはただのこれ👇

A()
B()

👉 普通のJSなので

A → B（上から）
